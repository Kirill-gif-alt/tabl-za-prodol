# Прогноз загрузки авиарейсов

Сервис считает, сколько пассажиров будет на рейсе в день вылета. Прогноз дается на четыре момента:
за 30 дней, за 14 дней, за 7 дней и за 1-3 дня до вылета. Ответ — число пассажиров, не доля.

Система учится на ваших данных. Ночью переобучается целиком, днем дообучается на свежих продажах.
RMS обращается к ней по REST: `POST /predict`.

## Как это устроено

Путь данных:

```
файлы (история, билеты, доступность)
   -> признаки (кривая продаж, история рейса, календарь)
   -> модели (среднее по истории, LightGBM, sequence-модель)
   -> стекинг (веса моделей по ошибке на свежих вылетах)
   -> критик (границы, выбор лучшей модели, проверка на NaN)
   -> ответ API
```

Что делает каждый шаг:

- **Признаки.** Из строки `CURVE` строится кривая «сколько продано к N дням до вылета». К ней добавляются
  средние по рейсу, направлению и дню недели, темп продаж, календарь.
- **Модели.** Для каждого горизонта обучены три модели. Если одной нет или она упала, остальные работают.
- **Стекинг.** Ансамбль смешивает модели с неотрицательными весами. Веса подбираются на последних по времени вылетах.
- **Критик.** Приводит ответ к границам `текущие продажи <= прогноз <= Total AU`. Выбирает модель с лучшей
  недавней ошибкой для этого рейса и горизонта. Отбрасывает NaN и бесконечности. Никогда не падает.

## Входные файлы

Все файлы — CSV. Разделитель определяется сам: запятая, `;` или табуляция. BOM допустим.
Даты: `ДД.ММ.ГГГГ` (также понимаются `ГГГГ-ММ-ДД` и `ДД/ММ/ГГГГ`). Регистр названий колонок не важен.

### SalesHistory.csv — история улетевших вылетов

Одна строка — один вылет `(REIS, FLYDATE)`.

| Колонка | Что это |
|---|---|
| `REIS`, `FLYDATE` | рейс и дата вылета (обязательные) |
| `CITY1`, `CITY2` | города вылета и прилета |
| `TICKETS` | итог пассажиров на вылете. Если пусто, берется сумма по `CURVE` |
| `REFUNDED`, `GROUP`, `CORP`, `REVENUE` | возвраты, признак группы, признак корпоратива, выручка |
| `CURVE` | продажи по дням: `"0:1 1:5 14:3"` |
| `REFUND_CURVE` | кривая возвратов (сейчас не используется) |

Как читается `CURVE`. Пара `d:n` значит «за `d` дней до вылета продано `n` билетов». Пример: `"0:7"` — семь билетов
в день вылета. `"0:1 1:5"` — один билет в день вылета и пять накануне.

- Мусорные куски пропускаются. Повторы одного дня складываются.
- Дни больше 180 сворачиваются в 180.
- Повторы `(REIS, FLYDATE)` в файле схлопываются, остается последняя строка. Повторная загрузка ничего не меняет.

### Tickets_SALE_Last14Days.csv и SalesTickets.csv — билеты

Нужны колонки `REIS`, `FLYDATE` и либо `DTD`, либо `DEALDATE`. Читаются еще `CITY1`, `CITY2`, `NFARE`, `RBD`, `GROUP`, `CORP`, `TYPE`.

**Персональные данные не читаются вообще.** Колонки с ФИО, PNR, контактами, датой рождения парсер не открывает:
он берет только перечисленные безопасные колонки. Строки с типом возврата (`REFUND`) пропускаются.

### Файл доступности — Total AU

Ежедневный файл по ближайшим вылетам. Колонки распознаются по именам, регистр и пробелы не важны:

| Что нужно | Какие имена понимаются |
|---|---|
| рейс | `REIS`, `Flight`, `Рейс` |
| дата | `FLYDATE`, `Date`, `Дата вылета` |
| **Total AU** (потолок) | `Total AU`, `TotalAU`, `AU`, `Capacity`, `Всего мест` |
| занято / свободно | `SegBkd`, `Booked` / `Free`, `Free SegBkd`, `Avail` |
| конфигурация | `Config` |

Правила:

- Из ячейки берется первое число: `Y180` -> 180.
- Если колонки Total AU нет, потолок восстанавливается из `Total SegBkd` или из суммы `SegBkd + Free`.
- Если потолка нет совсем, строка отбрасывается (с предупреждением в логе).
- Если файла доступности нет, потолок оценивается по истории: квантиль 0.99 по рейсу, не ниже максимума продаж.
  В запросе `/predict` Total AU приходит всегда, он главнее.

```bash
python -m training.full_train \
  --history input/SalesHistory.csv \
  --availability input/Availability.csv \
  --tickets input/tickets/SalesTickets.csv \
  --out artifacts
```

- `--tickets` можно указывать несколько раз.

- Версия пишется в `artifacts/v<дата>_<хеш>/`, указатель на текущую — `artifacts/current.json`.

- Запущенный API сам подхватывает новую версию (проверка раз в минуту). Можно и сразу: `POST /retrain`
  перезагружает модель после обучения.

## Примеры для RMS (curl)

Прогноз:

```bash
curl -s -X POST http://localhost:8000/predict -H "Content-Type: application/json" \
  -d '{"reis":"KV-110","flydate":"10.03.2026","current_booked":42,"total_au":100,"dtd":14}'
```

Поля запроса: `reis` — строка 1-16 символов; `flydate` — `ДД.ММ.ГГГГ`; `current_booked` >= 0 — продано сейчас;
`total_au` > 0 — потолок; `dtd` — от 0 до 180 дней до вылета.

Ответ:

```json
{
  "reis": "KV-110",
  "flydate": "10.03.2026",
  "horizons": {
    "30d":  {"pred": 48, "confidence": 0.62},
    "14d":  {"pred": 52, "confidence": 0.91},
    "7d":   {"pred": 55, "confidence": 0.80},
    "1_3d": {"pred": 57, "confidence": 0.71}
  },
  "critic": {"ok": true, "chosen_model": "lgbm_14d", "flags": []}
}
```

Коды ответа:

| Код | Когда |
|---|---|
| 200 | прогноз готов |
| 422 | плохой ввод; в `detail` понятный текст по-русски, в `errors` — поля |
| 503 | «Модель ещё не обучена» |
| 500 | внутренняя ошибка; текст без деталей, стек записан в лог сервера |

Состояние:

```bash
curl -s http://localhost:8000/health
```

Возвращает `status` (`ok` или `no_model`), версию модели, дату обучения, число вылетов, метрики и состояние фонового обучения.

Полное переобучение в фоне (токен берется из `FORECAST_ADMIN_TOKEN` на сервере):

```bash
curl -s -X POST http://localhost:8000/retrain -H "X-Admin-Token: $FORECAST_ADMIN_TOKEN"
curl -s http://localhost:8000/retrain/status
```

- Параллельно идет только одна задача. Второй запуск вернет 409.
- Без токена или с чужим токеном ответ 403. Если переменная `FORECAST_ADMIN_TOKEN` на сервере не задана, админ-эндпоинты закрыты совсем.
- Необязательное тело: `{"force": true}` — обучить заново; `{"synthetic": true}` — демо на синтетике.
- `POST /incremental` работает так же и запускает дообучение.
- `GET /retrain/status` показывает `idle`, `running`, `done` или `failed`.

## Ночной ретрейн и дневное дообучение

Ночью: полное обучение на всей истории (например, в 02:30). Днем: дообучение на свежих файлах (например, каждый час
или раз в день после выгрузки).

### Linux (cron)

```cron
30 2 * * *  cd /opt/flight-load-forecast && .venv/bin/python -m training.full_train --history input/SalesHistory.csv --availability input/Availability.csv --tickets input/tickets/SalesTickets.csv >> logs/full.log 2>&1
15 * * * *  cd /opt/flight-load-forecast && .venv/bin/python -m training.incremental --tickets input/tickets/Tickets_SALE_Last14Days.csv --availability input/Availability.csv >> logs/incr.log 2>&1
```

### Windows (Планировщик заданий)

Создайте два задания, из командной строки администратора:

```bat
schtasks /Create /SC DAILY /ST 02:30 /TN "Forecast nightly retrain" /TR "cmd /c cd /d C:\flight-load-forecast && .venv\Scripts\python -m training.full_train --history input\SalesHistory.csv --availability input\Availability.csv --tickets input\tickets\SalesTickets.csv >> logs\full.log 2>&1"
schtasks /Create /SC HOURLY /TN "Forecast incremental" /TR "cmd /c cd /d C:\flight-load-forecast && .venv\Scripts\python -m training.incremental --tickets input\tickets\Tickets_SALE_Last14Days.csv --availability input\Availability.csv >> logs\incr.log 2>&1"
```

Папку `logs` создайте заранее.

Заметки:

- Скрипты пишут новую версию рядом, API подхватывает ее сам (раз в минуту). Перезапуск API не нужен.
- Дообучение требует готовой полной версии. Если ее нет, оно вернет понятную ошибку.
- Повторный запуск с теми же файлами ничего не дублирует.
- Код возврата: 0 — успех (в том числе «версия уже есть»), 2 — плохие входные данные, 1 — сбой.

## Как читать метрики

Метрики пишутся в лог обучения и в `metadata.json` версии, а также видны в `GET /health`. Считаются по горизонтам
на последней по времени части данных (15%), которую модели не видели при подборе весов.

- `mae` — средняя абсолютная ошибка, в пассажирах. Чем меньше, тем лучше.
- `mape` — средняя ошибка в процентах от факта.
- `n` — на скольких примерах посчитано.
- Строки по моделям: `hmean`, `lgbm`, `seq`, `ensemble`.
- `_baseline_booked` — ошибка наивного прогноза «в день вылета будет столько, сколько продано сейчас».
  Ансамбль должен быть заметно лучше этой строки. Если нет, прогнозу рано доверять.
- Ошибка падает с приближением вылета: на 1-3 днях она самая маленькая, на 30 днях самая большая. Это нормально.

Поле `critic` в ответе:

- `ok` — `true`, если все четыре горизонта прошли без аварийных замен. `false` — пришлось падать до «текущих продаж» или вход был некорректный. Это не про точность прогноза.
- `chosen_model` — модель, чей ответ взят для ближайшего к `dtd` горизонта, например `lgbm_7d`. `ensemble_7d` — общий ответ ансамбля, `booked_7d` — аварийный ответ «столько, сколько продано».
- `flags` — пометки, по горизонтам (`7d:clipped_to_capacity`):

| Флаг | Что значит |
|---|---|
| `clipped_to_capacity` | прогноз был выше Total AU и обрезан до него |
| `clipped_to_booked` | прогноз был ниже текущих продаж и поднят до них |
| `total_au_below_booked` | во входе Total AU меньше проданного; прогноз равен проданному |
| `non_finite_model:<имя>` | модель вернула NaN или бесконечность; ее ответ отброшен |
| `fallback_model` | лучшая модель не подошла, взята следующая |
| `sparse_route` | у рейса мало истории; прогноз опирается на направление или общие средние |
| `far_from_horizon` | `dtd` далеко от точки горизонта; `confidence` занижен |
| `negative_model:<имя>` | модель вернула отрицательное число; ее ответ отброшен |
| `bad_input:current_booked`, `bad_input:total_au`, `bad_input:preds` | во входе некорректное значение; критик подставил безопасное |
| `total_au_zero` | Total AU равен нулю |
| `critic_error` | сбой самого критика; прогноз равен проданному, `ok=false` |
| `service_error` | сбой на этом горизонте в сервисе; прогноз равен проданному, `ok=false` |

`confidence` — число от 0.05 до 0.99. Оно падает, когда `dtd` далеко от точки горизонта и когда недавняя ошибка модели
велика относительно остатка к продаже. Это не вероятность в строгом смысле, а мера доверия для сравнения.

## Как достраивается кривая по запросу

В запросе есть только `current_booked` и `dtd`, а не вся кривая продаж. Поэтому система достраивает ее сама:

1. Берется типичная кривая: среднее по последним улетевшим вылетам этого рейса. Если их мало (меньше 3), по направлению, затем по всем.
2. Кривая подгоняется так, чтобы в точке `dtd` она проходила ровно через `current_booked`.
3. Прошлое (до `dtd`) восстанавливается по форме типичной кривой. Если накоплены ежедневные файлы по этому вылету, используется живая кривая из них.
4. Будущее (после `dtd`) строится по типичному приросту, масштаб берется по темпу продаж, не больше 4 раз и не меньше 0.25.
5. Кривая всегда монотонна.

Почему так: RMS обычно присылает одно число, а модели нужны темп продаж и форма кривой. Типичная кривая дает разумную оценку формы.
Цена такого подхода — темп восстановлен, а не измерен. Если у вылета есть живая кривая из ежедневных файлов, прогноз точнее.

Для горизонта, на который `dtd` не попадает, берется состояние вылета на точке этого горизонта по достроенной кривой.
Например, при `dtd=20` для горизонта 14d признаки считаются на 14 днях по прогнозной части кривой. Чем дальше `dtd` от точки
горизонта, тем ниже `confidence`.

## Защита от утечки будущего

Все исторические признаки (средние по рейсу, направлению, дню недели, доля групп, выручка) считаются только по вылетам,
которые уже улетели до даты прогноза: `flydate < flydate_рейса - dtd`. Вылет в тот же день, что и дата прогноза, тоже не учитывается.

- Если до даты прогноза не было ни одного вылета, признаки равны 0, а не среднему по всей таблице.
- Разбиение на обучение и проверку идет по времени, не случайно: проверка — последние по дате прогноза строки.
- В тестах есть проверка: в таблицу дописывается «ядовитый» вылет с огромным итогом, и признаки строк раньше его даты не меняются.
- Пассажирские данные (ФИО, PNR, контакты, дата рождения) в систему не попадают.

## Чего система НЕ делает

- Не предсказывает отмены рейсов, замену борта и сезонные события, которых нет в истории.
- Не знает цен и тарифных классов будущего: она видит только их след в продажах.
- Не обещает точность на новых рейсах без истории. Для них работает запасной уровень, а в ответе будет флаг `sparse_route`.
- Не строит прогноз выше Total AU и ниже уже проданного. Это жесткое правило критика.
- Не заменяет решения RMS. Это оценка спроса, а не рекомендация по ценам.
- Не хранит персональные данные пассажиров.
- Не заменяет ночное полное обучение дневным: дообучение лишь подстраивает веса и сдвиг, форму моделей оно не меняет.
- Не раздает и не проверяет пользователей: токен защищает только админ-эндпоинты. `/predict` и `/health` открыты, держите API во внутренней сети или за шлюзом.

## Про torch

`torch` необязателен, в `requirements.txt` он закомментирован. Если он установлен, sequence-модель работает как GRU/LSTM.
Если нет, она автоматически переходит на запасную ветку на `scikit-learn` (`MLPRegressor`). Интерфейс, имя модели `seq` и формат
ответа те же, качество может немного отличаться. После установки torch переобучите модель, чтобы sequence-модель перешла на torch.

## Подключение к сайту КРАСАВИА

Папка лежит внутри папки сайта и работает как «Модель 2» рядом с прежней моделью сайта.

0. Нужен Python 3.10 или новее (python.org, при установке отметьте «Add python.exe to PATH»). Скрипты сами ищут его и подскажут, если не найдут.
1. Один раз: `Install-Forecast.cmd` (ставит библиотеки, нужен интернет).
2. Обучение: перетащите `SalesHistory.csv` (или папку, где он лежит) на `Train-Forecast.cmd` (без своих данных — `Train-Forecast.cmd demo`).
3. Запуск: `Start-Forecast.cmd`. Если модель уже обучена, `Start-Krasavia.cmd` поднимает её сам, свёрнутым окном.
4. Ежедневно: `Update-Forecast.cmd "Tickets_SALE_Last14Days.csv" ["файл доступности.csv"]` — дообучение на свежих файлах.
5. В сайте: «Управление профилями» → «Функции» → «Вторая модель прогноза» — включить нужным профилям.

Что появляется в сайте: плитка «Модель 2» в карточке рейса (рядом с моделью 1), кнопка «Модели» в шапке и окно
«Сравнение моделей» (ближайшие рейсы обеими моделями, качество модели 2, проверка своего рейса).

Как это связано: браузер → сервер сайта (`/__krasavia/ml/...`) → служба на порту 8077. Другой адрес службы задаётся
переменной `KRASAVIA_ML_URL` (например, `http://192.168.0.10:8077`, если служба работает на другом ПК).
Если службы нет, сайт не ждёт её: в карточке написано «не запущена», остальное работает как раньше.
Для окна сравнения есть пакетный запрос `POST /predict_batch` (до 500 рейсов за раз, ответ про 200 рейсов — около секунды).
